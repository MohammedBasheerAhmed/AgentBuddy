# Audit 3: READ-side access evaluation (Agent Buddy, D:\AgentBuddy, 2026-11-07)

Scope: where results are produced, shown or concluded from data the signed-in user may only partly be allowed to see.
Method: read the docs named in the brief, then the readers, cards and checks. VERIFIED = I read the code path (or ran a pure module with node) and the behaviour follows from it.
ASSUMED = the code path is verified but the outcome depends on a ServiceNow behaviour nobody has checked on a live instance (several are already open questions in docs/live-questions).
Not re-reported: items in docs/review/audit-2026-11-04.md.

## The root causes in three sentences

1. The user's ROLES are read (g_user via the bridge) but used for exactly one thing, the first-run suggestion of a work profile. No feature, card, check or read is gated by role or by "can this user read/write this"; the panel assumes everyone is a fulfiller. (R-01)
2. Every "none" is trusted after `confirmEmptyIsReallyEmpty` (src/context/access.js:236-251) or, in many readers, with no probe at all. The probe proves only "this user can see ONE row of the table", never "this user can see the rows that belong to THIS record". Row ACLs, domain separation and per-account scopes pass it. (R-02)
3. `disp()` (src/context/util.js:27-30) returns the stored value when the display value is empty, and nothing downstream recognises a 32-hex sys_id as "I was not allowed to see the name". Field-level ACLs return empty values, and empty means "missing" everywhere it is checked. (R-05, R-08)

## Direct answers to (a)-(h)

(a) FIELD-LEVEL ACL: no code path asks "was this field readable?". pack.js drops empty values; missing.js, routing.js, resolutionCheck.js, CallerCard (`noCaller`) read absence as "nothing there"; people.js knows emails can be unreadable but its note never reaches the screen. The AI side is better (src/domain/parts.js:99 "empty, or not readable by your user"). See R-09, R-13, R-14.
(b) ROW-LEVEL ACL: `empty-or-hidden` is honoured only where a reader calls the probe, and the probe cannot detect partial hiding. Readers that call no probe: similar.js:167 and :258, related.js:160 (own table and `task`), :500, fix.js:158. Cards go 'clear' from an EMPTY in RelatedCard, OutageCard, RoutingCard, KnowledgeCard, StepsCard (all through `readFully`, which only knows the four bad statuses). The Caller card's one-line summary ignores access entirely (R-09). My work is the most careful screen; reports use `visibility()`/`verifiedCount` for zero counts but not for the Aggregate's own row-ACL behaviour (R-15).
(c) JOURNAL: see R-18/R-19. Work notes vs comments are separated correctly by element; unknown labels default to internal. Nothing is inferred from work notes the user cannot see because nothing says they might be missing.
(d) KNOWLEDGE: published + valid_to only; no can-read, no audience, no active, no retired check beyond `workflow_state` (retired/draft/review are excluded by the published filter). The panel offers and "Copy link ... share with the customer" for articles the customer may not open (R-10). The agent's own can-read is assumed to be applied by the Table API (open question, fix.md Q2).
(e) PEOPLE/PII/SENSITIVE: sensitivity = org policy + prefix list, not role (R-22); sys_user read is one small query, emails unreadable per field are not distinguished (R-14); reference-person names from other tickets are masked but their display falls back to ids (R-13).
(f) ROLES: read from `g_user` (classic/Workspace) or the portal's NOW/root scope (maybe null) and sent to the panel as `page.user.roles`; consumed only by the first-run profile suggestion (itil, itil_admin, sn_incident_write -> IT profile). Nothing else: the code assumes every signed-in user is a fulfiller who can read what the profile lists. `sys_user_has_role` is never read. R-01.
(g) ACCESS NOTES ON SCREEN: R-11, R-12. Insights cards use `plainNote` (partial); Knowledge screen uses `plainNote` (src/sidepanel/knowledge/Notes.jsx); My work/Reports use their own English sentences with labels (good, e.g. `accessNote`, `statusNote`); Check tab, AI-run errors, Chat card and `skipped` notes do not.
(h) CACHES: R-16, R-17. chrome.storage holds no ticket text except `lastViewed`; in-memory caches are per panel/tab, not per user. Reports cache is per user. Answers store key is `host|table:sysId` (no user).

## Already done well (so nobody re-fixes it)
- 403 / policy / ACL / rate limit / maintenance / HTML-page / timeout are told apart at the source and in the sentences (tableApi.js:116-138, access.js:76-109).
- Every list reader re-checks each row against the record (ignored-filter guard).
