# Audit 4: the WRITE side and role gating (read-only audit, 2026-11-07)

Scope: what Agent Buddy OFFERS and DOES versus what this signed-in user may do. Repo: D:\AgentBuddy (HEAD 0a1685f). Nothing in the repo was edited.
Evidence: code reading plus two scratch probes in this folder (`bridge-probe.js` loads the real `src/page/bridge.js` into a fake page;
`kinds-probe.mjs` imports the real feature registry). VERIFIED = read in the code or reproduced by a probe. ASSUMED = depends on how
ServiceNow itself behaves, which the repo's own docs mark as unchecked (docs/live-questions/assist.md Q9 and Q10, portal.md Q11).

## 0. The short answer

* The only thing Agent Buddy writes is `FILL_FIELD` (one whitelisted column per call, never a save). It never writes state, assignee, group,
  tasks or approvals. So "can this user assign / change state" is not a write problem; it is an OFFER problem (suggestions, labels, buttons).
* The ONE per-user writability check is `g_form.hasField` + `g_form.getEditableFields()` on a classic form. Everything else (visibility,
  mandatory, UI policy outcome, state transitions, record locked/closed, field-level write ACL beyond "is it editable on the form") is not checked.
* The user's roles ARE read (`g_user.roles`) and arrive in the panel (`page.user.roles`), but are used in exactly ONE place: the first-run
  suggestion of work profiles. Nothing is hidden, disabled or explained because of a role. A profile "only decides what is SHOWN"
  (src/profiles/profiles.js:6). Offers are decided by record KIND + profile + stage, never by capability.

## 2. Answers to the seven questions, with evidence

**(1) Every write: is the target checked first?** There is one write primitive (`FILL_FIELD`, src/content/fill.js:68) with these checks, in order:
whitelisted column (fillable.js:35-57); panel text reviewed for customer-visible fields (insertFlow.js:103-110); record must be the one the text was written for
(fill.js:38-47); bridge: `hasField` (bridge.js:817-822), `getEditableFields` membership ONLY when the list is non-empty (:824-827, W-01), HTML field type (:829-833),
choice list must exist on the form via `getOption` and read back (:838-848), length limits. Not checked: visibility, mandatory, UI policy result, State transition,
locked/closed record (except through W-01's list), field-level write ACL beyond "is it editable on the form", assignment of the record to the person. Failure behaviour:
`read-only`, `no-such-field`, `set-failed`, `no-such-choice` etc. return a plain reason (fillable.js:119-130) and the panel falls back to Copy (compose/shared.js:156,
ResultView.jsx:149); this is honest and NOT a silent no-op. The silent cases are W-01 (reports success), W-04 (code stays filled), W-05 (hidden field filled). Undo
(`restoreField`, bridge.js:868-901) has the same editable-list gap and otherwise refuses if the box changed. Prepare to close = 2 fields (close_code first, then notes),
incident only for the code (prepareClose.js:25).

**(2) Customer comment vs work note.** The panel knows per field which is customer-visible (`customerVisible`, fillable.js:35-57) and warns, reviews text, and refuses
work-note phrases in comments (review.js, security.md row "Customer-visible text"). It learns what the agent can post only through `hasField`/`getEditableFields`
(classic). It does not use channel (`contact_type`), caller=me, ticket kind beyond two cautions (fillable.js:150-151), nor Workspace composer state (W-12, W-13, W-02).

**(3) Role awareness.** Yes, one place; see section 3. Not used: Team (by profile only, W-14), approvals (My work reads only the user's own approvals, mywork/read.js),
reports across groups (membership scope), knowledge publish (W-19), assign-to-other (not a write here), SLA/CI/change-conflict cards (read, shown for kind+profile). A pure
fulfiller gets: AI actions limited by KIND (incident-only actions such as routing-hint, sentiment-risk (kinds: incident, case...), outage card, are not drawn on sc_task), but the
profile default is `it`, the checklist (req-only) is hidden, and the reply/missing-info offers point at comments the requester cannot read (W-02, W-03). An agent on an HR or CSM case
gets the right KIND features (hr-case-brief; account-briefing) only if the profile matches; otherwise a one-line hint offers to add it (profiles.js:200-209). HR has no Close well (W-09).

**(4) Kinds.** kinds-probe.mjs output (features per kind): incident 21, problem 11, change 3, request 15, requested_item 21, catalog_task 19, case 22, hr_case 13, task 12, other 2.
`other` gets summary + catch-up only, 13 readable columns, no cards, no explanation (W-11). Custom tables extending `task` are resolved to their real class for reads but still map to `other`.

**(5) AI and access.** In the prompt: only what the user's own session could read (reads are the user's; 403/empty become `access` entries and the "Not available" part), so the prompt does not
exceed the user's read access. In suggestions: the model is never told the user's capabilities; routing group can be inactive (W-15); next steps may need roles (W-16); `prepare-close` code comes from
look-alikes and is only applied if the form lists it (`getOption`, bridge.js:838), otherwise the panel names the code to pick by hand (insertFlow.js:353).

**(6) Cheap invisible checks.** See section 4.

**(7) What the bridge can provide without REST.** See section 3.

## 3. What the code knows about the user's roles (quotes)

* Bridge reads them: `roles: rolesOf(u)` (src/page/bridge.js:733); `rolesOf` accepts an array or a comma list, 200 names, 80 chars each (:83-91). Portal pages: `roles: rootLevel ? null : rolesOf(obj)` (:132), and docs/live-questions/portal.md:74 says "Assumed: not available; `roles` is then an empty list. Nothing in the panel depends on roles today."
* Content script cleans and forwards them: `roles` in `cleanSessionInfo` (src/content/sessionToken.js:91-97); `user: session && (...) ? { name: session.name, roles: session.roles, userId: session.userId } : null` (src/content/index.js:140). When the page gives no user, the fallback `lookUpMe` returns `roles: []` (sessionToken.js:118).
* Panel uses them once: `roles={Array.isArray(page?.user?.roles) ? page.user.roles : []}` (src/sidepanel/FirstRun.jsx:27) -> `suggestProfiles` -> `ROLE_RULES` (src/profiles/profiles.js:73-79: `it: ['itil','itil_admin','sn_incident_write']`, `csm: prefix ['sn_customerservice','sn_csm_']`, `hr: prefix ['sn_hr_core.','sn_hr_le.','sn_hr_sp.']`, `km`, `mpc`). The sentence in profiles.js:6: "A profile only decides what is SHOWN."
* No other file reads `.roles`: grep of src/ for `g_user|hasRole|sys_user_has_role|itil_admin|sn_incident_write|sn_customerservice_agent|approver_user` finds only bridge.js, sessionToken.js comments, and profiles.js:74. There is no `sys_user_has_role` read and no admin probing (bridge.js comment line 721: "No admin probing").
* What it assumes otherwise: that anyone who can open a record may be offered every action for that kind, and that ServiceNow will refuse what the user cannot do. In practice the panel's only "no" is the field-state check.
