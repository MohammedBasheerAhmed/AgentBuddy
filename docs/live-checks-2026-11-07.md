# Live checks on dev364920, 2026-11-07

What was measured on the real ServiceNow developer instance (`dev364920`, Zurich-family UI) while answering the open questions of the
audit of 2026-11-07 (`docs/live-questions/audit-1107-*.md`). Read-only: `GET` requests with the signed-in session and the page's
`X-UserToken` (the same way the extension reads), no writes. Three users: the administrator (`admin`), **ITIL User** (`itil`, direct
role `itil` only) and **Abel Tuter** (`abel.tuter`, no roles), reached through the normal "Impersonate user" menu and ended after the
checks. The instance is a developer instance with demo data: where a result depends on a customer's configuration it says so.

## What is settled

| Question | Result | Where it matters |
|---|---|---|
| Where did `ui_page` come from? | The classic home page is a UI Page record: `/now/nav/ui/classic/params/target/ui_page.do?sys_id=<hex>` (inner frame `/ui_page.do?sys_id=<hex>`). Every user lands on it, requesters included. The old code read `<name>.do?sys_id=` as a record of table `<name>`. `ui_page` is not a table here (`sys_ui_page` is). | Record gate (`isTicketTable`, `src/context/kinds.js`) |
| Where is `g_user`? | Classic form frame: yes (`roles` is an array of 124 for the admin, `getRoles()` and `hasRoleExactly()` exist). Next Experience shell (top window): **no**. Service Operations Workspace (home and record): **no** (`NOW.user` has only `userID` and `isImpersonating`). The classic home page's inner frame has one. | Roles are unknown on Workspaces: `src/page/bridge.js` `rolesOf`, `src/profiles/` |
| What does a closed form report as editable? | `getEditableFields()` on a closed incident returns a **non-empty** list (10 fields) without `state`, `short_description` and `close_notes`; `isReadOnly('short_description')` is true. `active` is not a field of the incident form. | Read-back and locked-field rules (`writes-*` tests) |
| How is a field the user cannot read returned? | **Omitted entirely** (the key is missing), not an empty string: asking an ITIL User for `roles, locked_out, hashed_user_id, accumulated_roles, password_needs_reset, email, title` on a user record returned only `email, name, title, user_name`. | `pack.unreadable` and the "could not read it" lines (`src/context/`, honesty tests) |
| What does a row-filtered read return? | `200` with `[]`; `X-Total-Count` still shows the unfiltered total (`sys_properties`: 0 rows, total 3,805). Abel Tuter reading `incident`, `kb_knowledge` and `sc_task` gets `200` and no rows. | `confirmEmptyIsReallyEmpty`; never say "none" from an empty page alone |
| What does a table-level refusal say? | `403`, message `User Not Authorized`, detail `User is unauthorized to access table: sys_documentation`. That is an ordinary role rule, **not** a REST API policy. A query on a denied column says `Insufficient rights to query records` / `Field(s) present in the query do not have permission to be read`. | `deniedReason` (`src/context/access.js`) |
| Are query conditions silently dropped? | Yes: the UI itself shows "Part of the query on sys_choice has been ignored because of insufficient access for 'query_match' operation on sys_choice.name". | A filtered count may be too large: say "at least" |
| Can an agent read `sys_choice`? | **No**, in any query shape, for a plain ITIL User (`403`). | Choice labels must not come from `sys_choice` |
| Where do choice labels come from for an agent? | `/api/now/ui/meta/<table>` answers `200` for the ITIL User and for Abel; each column carries `label` and `choices` (`1=New, 2=In Progress, 3=On Hold, 6=Resolved, 7=Closed, 8=Canceled`). The record's own display values (`sysparm_display_value=all`) also work. | Choice and field labels |
| Can an agent read `sys_documentation` / `sys_db_object`? | The ITIL User (direct role `itil` only) can: `interaction_agent` is **inherited** through `itil`'s role chain, which `sys_documentation`'s read rule asks for. `sys_db_object` returns `name, label, super_class`. Abel (no role) is refused on `sys_documentation`. A fulfiller without `itil` was not tested. `sys_dictionary` returns no rows. | Optional table-label source; the built-in list and `sys_class_name` display values stay first |
| Does `kb_view.do` redirect to a portal? | No. `sn_km_portal.glide.knowman.serviceportal.enable_redirect` is `false` here. The reader opens the article directly. For Abel (no roles) two of three tested articles rendered a full article page; the Table API gave him no `kb_knowledge` rows. | One reader link for articles (`src/lib/snLinks.js`) |
| Do the portal page ids exist? | `sp_page` has `ticket`, `sc_request`, `kb_article`, `kb_article_view`. `csm_ticket` and `hr_ticket` do not (CSM and HR are not installed here). Portals present: `sp`, `esc`, `kb`, `mesp`, `cab`, `swp`, `aiuxsp`, `benchmarks`, `perf`, `sp_config`. | Portal page table in `src/lib/snLinks.js` |
| The real state values | incident 1/2/3/6/7/8; problem 101/102/103/104/106/107; change_request -5/-4/-3/-2/-1/0/3/4; **task** (and `sc_task`, `sc_req_item`, which inherit it) -5/1/2/3/4/7; `change_task` -5/1/2/3/4 (3 Closed, 4 Canceled); **`problem_task` 151/152/154/157**; `sc_request.request_state` requested ("Pending Approval") / in_process ("Approved") / closed_*; `sc_req_item.stage` delivery / waiting_for_approval / fulfillment. | `src/domain/states.js`, `docs/states.md` |
| Who can read an `sc_task`? | A read rule with the condition `opened_by` = the user, plus scripted rules. `task.comments`, `incident.comments` and `sc_task.comments` have **no field rule**, so whoever can read the record reads its comments. `task.work_notes` needs `itil` (or `sn_*_read`). So "the requester does not see catalog-task comments" is **not guaranteed**: it depends on who `opened_by` is. | Wording stays "the requester may not see this" |
| The Workspace composer | Two boxes: `name="work_notes"` (aria-label "Work notes") and `name="comments"` (aria-label "Comments"), only the selected one visible; the other is 0 by 0. Buttons "Post Work notes", "Post Comments", "Save", "Resolve". The tab "Work notes" has `aria-selected`. No frames, 2,008 nodes in 462 shadow roots, a full search takes 7 ms. | `src/page/bridge.js` composer rules (the box is found by its `name` attribute) |
| Does a catalog item keep fulfilment instructions? | No. `sc_cat_item` has `description` and `short_description` (the requester's text), `delivery_plan`, `group` (fulfilment group) and `meta`, but no instruction field. The task's own `description` and `special_instructions` are where the steps live. | F21 not built; the checklist keeps reading the task |
| Who may create a knowledge article? | The `kb_knowledge` create rules have **no roles**: creation follows each knowledge base's contributor criteria. The roles that exist are `knowledge`, `knowledge_manager`, `knowledge_admin`, `knowledge_group_manager`, `knowledge_coach`, `knowledge_domain_expert`, `knowledge_group_member`, `knowledge_view_as`. | W-19 not built: a role gate would hide the button from people who can use it |
| REST without the token | `401 User is not authenticated` although signed in: the `X-UserToken` header (`g_ck`) is required, as the extension does. | `src/content/sessionToken.js` |

## Not settled (needs a customer-like setup)

- An external, portal-only user (`snc_external`): `kb_view.do` and the portal pages were not tested for one.
- A fulfiller who does not have `itil` (catalog-only, HR or CSM agents): `sys_documentation`, `sys_db_object`, `sys_choice`, `ui/meta`.
- A reference to a table the user cannot read: whether its `display_value` is empty or the sys_id. (Every reference tried was readable.)
- The wording of a REST API access policy refusal (the role `snc_platform_rest_api_access` is part of `itil`).
- Arabic and German label wording on a Workspace; Edge and Firefox on a real instance.
- A customer's own Workspace composer, if it is not the stock one.
